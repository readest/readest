#6521 (2026-10-01, iPadOS 27, 0.12.10): IMSLP score PDF (74 pp, pages 2+ are 1-bit CCITT ~9000x12000 = 108 Mpx) exits to library after ~5-6 swipes.

**Proven on iPad Air M2** via `idevicesyslog` (no JetsamEvent .ips is written for this!): `com.apple.WebKit.GPU exceeded mem limit: ActiveSoft 300 MB`, killed at 307-455 MB x3, then `WebPageProxy::processDidTerminate reason=GPUProcessCrashedTooManyTimes`. Different from [[pdf-ios-webcontent-oom-zoom-5118]] (WebContent canvas). **Mozilla's hosted viewer in iPad Safari crashes the same way** (page 7 one run, 11-12 another).

**Mechanism (pdf.js 6.2.108 AND 6.4.244):** `ImageResizer._createImage` encodes the full-size BMP and decodes it via `ImageDecoder`/`createImageBitmap` BEFORE downscaling -> ~430 MB bitmap in the GPU process. `canvasMaxAreaInBytes` only sets the target; the full decode still happens (built+device-tested: still crashed). `#rescaleImageData` (JS, no bitmap) only runs above 2 GB. `maxImageSize` blanks images; `isOffscreenCanvasSupported:false` moves the 430 MB to a main-thread canvas. Upstream #21794 / bugzilla 2063570 fixed only JPEG (ImageDecoder reduced frame).

**Desktop Firefox measurement (Playwright firefox, hosted viewer pdf.js 6.4.244, `measure.cjs` recipe: setInputFiles('#fileInput'), set PDFViewerApplication.page, wait renderingState===3, sum ps RSS):** tab content process 385 MB idle -> 2.6 GB peak by page 7; gs-downsampled 300 dpi control of the same file peaks 628 MB. Hosted viewer rejects cross-origin `?file=`.

**Status:** worktree `readest-fix-pdf-huge-image-gpu-oom-6521` has foliate `canvasMaxAreaInBytes` on mobile (insufficient alone) + vitest + a browser test (`pdf-huge-image-decode.browser.test.ts`, fake worker via `globalThis.pdfjsWorker`, spies ImageDecoder/createImageBitmap) that fails today. chrox rejected a pnpm patch (also: the min worker is one 991 KB line -> 1.6 MB patch). Duplicate search done (GitHub + Bugzilla): none. pdf.js FAQ: Safari "not fully supported", so file upstream with the Firefox numbers. #6232 likely same bug.

**Mitigation experiments on iPad (2026-10-01), carnaval paged 1->74, first blank page:** cap only (current) = p14 / p23; cap + `page.cleanup()` after each draw = p19 / p24 -> cleanup/cache size is NOT the lever; the transient full-size decode is. Blank page = GPU process killed once (WebKit restarts it, every drawn canvas loses pixels, pdf.js never redraws); reopen fixes. 3 kills in seconds = exit to library. **Text-layer-only benchmark (Firefox, 74 pp, wasmUrl REQUIRED or CCITT/JBIG2 silently render blank):** text only +86 MB (score) / +95 MB (WBE text book); render +2,158 MB / 54 s (score) vs +93 MB (WBE). MuPDF-for-pixels + pdf.js-for-text split: chrox said SKIP for now (mupdf npm 1.28.1 AGPL, ~10 MB wasm, likely whole-file in wasm heap).

**Blank-page root cause (chrox device test 2026-10-01):** after the first WebKit GPU-process kill, text PDFs still render but EVERY image decoded in the pdf.js worker stays blank, even in a newly opened book (new worker) -> worker OffscreenCanvas/createImageBitmap never reconnects to the restarted GPU process (WebKit bug); only an app restart (new WebContent) recovers. Not a cache: `page.cleanup()` after draw (B) = no change.
**Config levers exhausted:** iOS 27 has NO `ImageDecoder` (logged `ImageDecoder=undefined`), so `isImageDecoderSupported` is moot; `isOffscreenCanvasSupported:false` (H) = zero GPU kills but every scan blank (main-thread full-size temp canvas over WebKit's canvas limit); cap (A) = fewer kills, blank at p14-23. Only real fix = avoid the full-size decode (pdf.js upstream). xctrace Activity Monitor does NOT see Readest's WebKit GPU/WebContent footprint (flat 16/198 MB while paging) and the first segment after a launch never saves; use syslog. Readest.log via plugin-log flushes late; test builds should write a result file instead (`pdf-mem-applied.json` via plugin-fs).

**FIXED without patching pdf.js (2026-10-01, iPad-VERIFIED: carnaval 1->74 incl. fast swipes, all sharp, ZERO GPU kills in syslog):** Readest's worker wrapper (document.ts `configurePDFWorker`, now used on mobile WebViews too) inlines `src/libs/pdfImageShrink.ts` via `Function.toString()`: overrides worker `createImageBitmap` for huge `image/bmp` blobs (decodes pdf.js's own 1/24/32-bit BMP in JS, box-filters to ~12.6 Mpx) + `OffscreenCanvasRenderingContext2D.drawImage` (divides pdf.js's full-size source rect by the factor AND CLAMPS it to the bitmap). foliate pdf.js on mobile: `canvasMaxAreaInBytes` (routes huge images into the BMP resizer), `isImageDecoderSupported:false` (Android Chromium would bypass the hook), `useWorkerFetch:false`, absolute `pdfjsURL()` decoder URLs.
**Traps found:** (1) WebKit `drawImage` with a source rect overshooting the image by <1 px DRAWS NOTHING (Chromium clips) -> every scan blank on iOS while Android was fine; tests must use sizes NOT divisible by the shrink factor (4103), and run in WebKit (throwaway `mergeConfig` config, `instances: [{browser:'webkit'}]`). (2) relative pdf.js decoder URLs resolve against a `blob:` worker. Safari Web Inspector Network tab (chrox) showed the BMP blob rendering fine = decode OK, hook path broken. Android: hook verified via CDP worker auto-attach (`Target.setAutoAttach flatten`), `cdp-tap.cjs` recipe; VIEW-intent open after `adb push` when BookDrop is unreachable. Not yet committed; foliate change needs its own PR + re-pin.

**Final design (2026-10-01, iPad 1->74 sharp, 0 GPU kills; Xiaomi verified):** foliate passes only `canvasMaxAreaInBytes` + `useWorkerFetch:false` on mobile (+ absolute decoder URLs). `isImageDecoderSupported:false` was DROPPED: it also disables native JPEG ImageDecoder for every PDF on Android; instead the hook makes `ImageDecoder.isTypeSupported('image/bmp')` resolve false (pdf.js's resizer is the only BMP user). Benchmark (bench2.cjs, 74pp carnaval): WebKit GPU 3232->605 MB, WebContent 1751->983, Chromium renderer 3637->1034, Firefox tab 4020->1297; fix is also faster (WebKit 54s->26s). Xcode Activity Monitor/sysmon on iOS 27 repeats ONE stale sample for WebKit extension processes -> useless; count syslog over-limit/kills instead.
