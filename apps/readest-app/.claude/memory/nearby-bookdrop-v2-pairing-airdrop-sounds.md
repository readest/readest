**Item 3 WebRTC research verdict (checkout `~/dev/localsend`, tracks upstream to ~3 commits, app v1.18.2):** LocalSend's WebRTC CANNOT transfer across networks as-is.
- It lives in the reusable Apache-2.0 Rust core crate `packages/core/src/webrtc/` (webrtc-rs, no Flutter dep) behind a `webrtc` cargo feature - the same crate Readest already embeds.
- But the signaling server rooms peers BY PUBLIC IP (`server/src/util/ip.rs`) - two devices on different networks never see each other, by design (it's a same-LAN fallback for when multicast is blocked). STUN only, NO TURN relay. And upstream ships it HARD-DISABLED (`webRTCEnabled = false` since 2026-07): send path never wired, receive stubbed, pairing hardcoded-refused, a latent Ed25519/RSA key-type bug.
- So true cross-network P2P = our own signaling server (re-roomed by pairing) + TURN + finishing abandoned code in our fork. Rejected (Approach B) for that cost + both-devices-online requirement (bad for sleeping e-readers). Chose the cloud-relay path (C) instead.

**Pairing trust anchor = the TLS cert fingerprint ONLY.** The Rust receive path (`service.rs` PrepareUpload) now sets `cert_verified = cert_fingerprint.is_some()` and passes it through `SenderPayload.cert_verified` to the webview. Auto-accept requires cert_verified true; cert-less senders (the stock LocalSend Flutter app, which falls back to the spoofable body fingerprint at `service.rs:347`) can NEVER be paired and always confirm. `canAutoAccept(sender, entitled) = entitled && sender.certVerified && isPairedDevice(fingerprint)`.

**AirDrop-responsive presence (chrox request, second session pass).** Peers appear/disappear with screen state, no connect/disconnect teardown. Three parts, all confirmed against the crate: (1) Rust `service.rs device_payloads` prunes any peer whose last `StatefulDevice.logs` timestamp is older than `PRESENCE_TTL` (4.5s) - `device_is_present(last_seen, now)`: Some->age<=TTL, future(clock skew)->present, None->absent. (2) While the picker is open (`status.running && !sendState`), a 1.5s heartbeat in `DevicePickerDialog` calls `announceLocalSend(false)` (multicast only, no subnet scan) + re-lists; live peers keep answering so the crate's `state.found` refreshes their timestamp, a locked peer stops answering and ages out. TTL 4.5s vs 1.5s beat = ~3 beats margin so one dropped packet never flickers a live peer. (3) New Tauri command `localsend_set_discoverable(active)` -> crate `set_answer_announcements(active)` + re-announce on wake; `LocalSendManager` drives it from `document.visibilitychange` (fires on BOTH mobile background and desktop screen-lock). `answering=false` gates BOTH answering-with-register AND learning-from-announcements in the crate, so a hidden device vanishes from every viewer within the TTL and reappears within one round-trip on wake. Registered the command in all 4 ACL places + `permissions/autogenerated/localsend_set_discoverable.toml`. Rejected an HTTP liveness probe: a desktop peer that locks keeps its HTTP server up (probe would wrongly keep it visible); the answer-gate hides it correctly on both platforms. Rust test `presence_ttl_keeps_recent_and_drops_stale`.

Symptom (chrox, macOS release .app + Xiaomi 368b0948 both foregrounded, Android screen on): after tapping refresh on macOS the Android peer showed for ~2s then disappeared. Root cause: the pass-2 presence heartbeat announces MULTICAST ONLY, but the peer was first found by the one-time unicast subnet SCAN; on this Wi-Fi multicast does not complete Mac<->Xiaomi (MIUI power management / AP multicast filtering), so `last_seen` was never refreshed and the peer aged out at the 4.5s `PRESENCE_TTL`. The 2s appearance PROVES outbound LAN + the peer's HTTP server work (curl `POST /api/localsend/v2/register` to the phone returned 200); only the multicast keep-alive was missing - so the earlier "Local Network permission" hypothesis was WRONG and abandoned. Fix (Mac-side ONLY, no crate change, no Android rebuild): on every `localsend_announce` beat, after the multicast announce, re-probe the KNOWN peers over unicast. New pure helper `service::known_reprobe_channels(&[StatefulDevice]) -> Vec<HttpChannel>` (collects each peer's confirmed `device.channel.http().cloned()`), wired in `commands.rs localsend_announce` via the crate's `DiscoveryHandle::discover_known_http_channels(channels)` - a TARGETED unicast probe, NOT a `/24` sweep; each probe's internal `found()` refreshes `last_seen`. Presence-on-lock is preserved: a mobile peer that backgrounds is OS-suspended so the unicast probe times out and it still ages out; a locked DESKTOP peer whose server keeps answering would stay visible (minor, acceptable, defensible). Rust test `known_reprobe_channels_collects_each_peers_confirmed_http_channel`. **VERIFIED on macOS** by reproducing the picker heartbeat in the app DevTools console (context = top `reader` frame; `window.__TAURI_INTERNALS__.invoke`): seed `localsend_announce{scan:true}`, then 15x `announce{scan:false}` + `list_devices`. Because the ~4.2s beat gap is under the 4.5s TTL only via the per-beat refresh (a once-seeded peer with no refresh would be pruned by +21s), persistence to +75s is direct proof the reprobe refreshes `last_seen`.
