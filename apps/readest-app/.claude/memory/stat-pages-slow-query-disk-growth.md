Prod Supabase project "Readest App" ref `vbsyxfusjjqdxkjqlysc`, **PG 15.6**, Small compute (1.94 GB RAM, 512 MB shared_buffers, 2 vCPU), `/data` 50.6 GB at 85% full. DB 39 GB. Read-only SQL via Management API works with the CLI token from macOS keychain (`security find-generic-password -s "Supabase CLI" -w`, strip `go-keyring-base64:` + base64 -d) -> `POST api.supabase.com/v1/projects/<ref>/database/query`; edge/postgres logs via `/analytics/endpoints/logs.all?sql=` (BigQuery dialect, `metadata.request/response`, `response.origin_time`). `pg_stat_statements` lives in schema `extensions`. Use `TABLESAMPLE SYSTEM (2)` for distributions; a full GROUP BY over 50M rows would evict the tiny cache and stall prod.

**Findings (2026-08-23):**
- The "avg 25979 ms" for `GET /rest/v1/stat_pages?user_id&book_hash=in&start_time=in` was ONE request (edge log max of that hour); that shape runs ~9/s (2.27M calls / 70 h), DB mean 3.7 ms, max 7.6 s, ~137 buffer hits/call. It is the push handler's existing-row lookup (`sync.ts` ~L788, before `pickWinningPages`). PK is `(user_id, book_hash, page, start_time)`; `start_time = ANY(...)` sits after the unconstrained `page` gap, so on PG<=16 nbtree re-walks the whole (user, book) range once per array element (500-batch x 17k-row book = the 7.6 s maxima). Proper fix: one RPC `INSERT ... ON CONFLICT DO UPDATE SET duration = greatest(...)` (the original spec design) instead of select+upsert; do NOT add a `(user_id, book_hash, start_time)` index (another ~5 GB).
- Slow requests cluster into all-route stalls (Cloudflare 520/522/525 = Kong/PostgREST unresponsive, even TLS handshakes fail): instance had ~658 MB in swap, iowait ~5%. Root cause = memory pressure, not the plan. Fix = bigger compute (Medium 4 GB min, Large 8 GB better) and shrinking the working set.
- stat_pages: ~50M rows, heap 6.2 GB + pkey 7.6 GB (~162 B/entry, ~2x bloat) + `(user_id, updated_at)` idx 2.4 GB = 16.5 GB = 42% of DB. Launched 2026-06-16 (#4606); ~6.3-6.9M rows/week (~27-30M/month, ~9 GB/month all-in). ~36k users with stats; avg ~1.5k rows/user, p50 350, p90 4k, p99 17k, max 73k; 87% of rows in the ~10k users >1k rows. 84% of rows have `updated_at` >7 d old, 44% >30 d. `ext` and `deleted_at` are never used (0%). `start_time` is SECONDS everywhere (app `nowSec`, KOReader, 0 ms-epoch rows in sample).
- Other fat: `auth.audit_log_entries` 5.35 GB / 17.4M rows since 2024-12; `auth.refresh_tokens` 3.5 GB / 8.4M rows; `books` 5.8 GB; `files` 3.6 GB.
- Retry storms (~2.5k failing req/day): `POST google_iap_subscriptions` 400 "date/time field value out of range: <13-digit ms>" 948/day (`src/libs/payment/iap/google/server.ts` upsert ~L53); `POST stat_books` 400 "unsupported Unicode escape sequence" 475/day (`\u0000` in title/authors, `sync.ts` ~L762; the client retries forever so that user's stats never sync); `books_pkey` duplicate 409 ~910/day.
