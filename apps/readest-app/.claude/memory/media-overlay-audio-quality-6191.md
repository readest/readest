# Media Overlay audio quality — #6191

Investigation on 2026-09-19; root cause not yet confirmed. No application code changed.

- Report: Windows 11 24H2, Readest 0.12.8, Edge 152; embedded EPUB narration allegedly degrades over time. Issue has two MP3 output recordings, no EPUB, speed settings, or comments.
- `MediaOverlayClient.ts` is identical in v0.12.8 and the investigated checkout. Windows uses an HTMLAudioElement with a blob URL, `preservesPitch = true`, and the configured playback rate. This path does not use BufferedTTSClient, WebAudioPlayer, or Readest's PCM timeStretch/resampling path.
- `DEFAULT_TTS_CONFIG.ttsRate` is 1.3 in both versions; useTTSControl applies the saved TTS speed to narration. This does NOT establish the reporter's speed.
- Downloaded issue attachment to `/tmp/readest-6191-audio.zip`, extracted into `/tmp/readest-6191-audio/`. Both output recordings are mono 44.1 kHz LAME MP3s, approximately 126 kbps. These are recording properties, not proof of the embedded source format or playback sample rate.
- Decoded with ffmpeg to 16 kHz float PCM for comparative analysis only. Across six-second energy-envelope windows starting at Storyteller times 5, 15, 25, and 35 seconds, the best matching relative rate was consistently 0.950 (Readest/Storyteller), with correlations 0.926, 0.901, 0.850, 0.829. Matching Readest start times: 5.11, 15.64, 26.16, 36.69 seconds. Different recording lengths alone were not used to infer speed.
- Compared detrended log spectra in 438 matched voiced 60 ms windows, searching frequency scale 0.90–1.10. Best mean correlation at frequency scale 1.000: 0.682, versus 0.031 at 0.950. Evidence is consistent with differing tempo while preserving pitch, rather than a simple sample-rate/pitch mismatch. Cannot identify either player's absolute speed or prove the cause of progressive degradation from these recordings.
- Chromium AudioRendererAlgorithm chooses passthrough near 1.0 with preservesPitch enabled and WSOLA otherwise. Source: https://chromium.googlesource.com/chromium/src/+/HEAD/media/filters/audio_renderer_algorithm.cc . Browser time stretching is a plausible quality contributor, not a confirmed diagnosis.
- Validation: `pnpm exec dotenv -e .env -e .env.test.local -- vitest run src/__tests__/services/tts/media-overlay-client.test.ts`: 39/39 passed. Fake media pipeline does not verify audible quality. `pnpm test -- <file>` unexpectedly started broad tests in this environment; stopped that owned process and used explicit vitest run.
- Next evidence: affected EPUB, actual rates in both apps, and same passage at exactly 1.0x. If it still degrades at 1.0x, isolate standalone audio playback in the same Windows Edge/WebView2 runtime from Readest's Media Overlay orchestration. Do not disable pitch preservation or replace the audio pipeline speculatively.

## Follow-up: 1.0x works, Rust playback options

- Reporter confirmed at https://github.com/readest/readest/issues/6191#issuecomment-5733414569 that 1.0x seems fine and their previous rate was 0.95x. This supports the tempo-processing hypothesis, but exact WebView2 reproduction remains outstanding.
- Windows desktop uses Edge WebView2, not the Edge browser application. Tauri config uses embedBootstrapper for the runtime. Chromium/macOS tests cannot establish a Windows/WebView2-specific defect.
- SpeedRuler allows 0.05 increments. TTSPlayerSheet.handleSelectRate writes both book and global ttsRate; loadBookConfig inherits global settings. No hardcoded 0.95 default or automatic rate adjustment found. Cannot determine how this reporter acquired that saved setting.
- Chromium has previously documented audible WSOLA artifacts near 1.0: https://chromium.googlesource.com/chromium/src/+/86ca53e6d1a1bfc0c218cd517f1d43de60ac64ef . Historical mitigation used resampling with a pitch shift, not evidence of the exact current WebView2 behavior.
- Local isolated capture completed using Playwright Chromium 148.0.7778.96 on macOS, HTMLAudioElement -> MediaElementAudioSourceNode -> ScriptProcessor, with output silenced after capture. Same Storyteller recording at 1.0/preserved, 0.95/preserved, and 0.95/unpreserved. Artifacts/script in /tmp/readest-6191-audio/. At 1.0, matched 2s waveform windows correlate 0.998/0.957/0.985 with source. 0.95 capture comparisons do not establish a close waveform match to reporter output; do NOT call the reported distortion reproduced. Browser helper daemon failed to start, so used installed Playwright directly for isolated capture.
- Existing handwritten timeStretch.ts is used by BufferedTTSClient web/desktop TTS, NOT MediaOverlayClient. Desktop native-tts playout methods currently return UnsupportedPlatformError; iOS/Android already have platform-native narration players.
- Rust options: rodio Player.set_speed shifts pitch along with speed (docs.rs/rodio/latest/rodio/struct.Player.html). Rust soundtouch bindings expose set_tempo preserving pitch, but SoundTouch itself uses WSOLA-like processing (soundtouch.surina.net/README.html). Rubber Band uses a different phase-vocoder-based engine and supports streaming/dynamic tempo through native bindings (breakfastquay.com/rubberband/technical.html and integration.html). A native player would bypass WebView2; merely using rodio's speed knob is not equivalent to pitch-preserved tempo.
- No application code changed or dependency added. Native backend evaluation should compare narration quality near 0.95x and typical faster rates, retain original-media position for SMIL highlighting, handle seek/flush/latency and streaming, and retain web/mobile platform paths. Replacing desktop narration is separate from removing handwritten WSOLA from buffered TTS.
