**Why this is right (KOReader facts, verified in ~/dev/koreader master 803d32ada):** KOReader disables Wi-Fi on EVERY suspend for `hasWifiToggle` devices (generic `onPowerEvent`), so after a wake the radio is always off; only `auto_restore_wifi` (`hasWifiRestore`: Kobo, Kindle, Cervantes) restores it silently and broadcasts `NetworkConnected`. `goOnlineToRun` returns false WITHOUT running the callback unless `wifi_enable_action == "turn_on"`, so "prompt" users (KOReader default) never had an offline close push anyway. Official kosync forces "turn_on" for auto sync on seamless devices (which is exactly the 30 s scan #5838 complains about) and since 2026 queues close-time progress (KOSyncQueue) "instead of blocking with goOnlineToRun". The old plugin stacked THREE ConfirmBoxes per open/wake (one per pull) in prompt mode.

**Cost to state in the PR:** "turn on" users WITHOUT "Restore Wi-Fi connection on resume" lose at-home open/wake sync until they enable that KOReader setting; devices without `hasWifiRestore` (PocketBook, reMarkable) need Wi-Fi toggled manually. **Why DRAFT (adversarial review, verified in code):** (1) `SyncAnnotations:getAnnotations` filters with the GLOBAL `settings.last_notes_sync_at` and a successful PULL advances it (`readest_syncannotations.lua:488`), so an annotation made while pushes fail is orphaned by the next online pull of ANY book until "Full sync all annotations"; pre-existing, but this PR exposes it to turn_on users at home whose Wi-Fi now stays off after wake. Push-before-pull does NOT fix it without splitting the cursor (the shared cursor then makes the pull miss remote notes); real fix = per-book push cursor in `doc_settings.readest_sync`. (2) progress/library row of a book closed offline sync only when that book is reopened + page turn (no queue; kosync has KOSyncQueue). (3) turn_on + auto_restore_wifi off (kosync forces turn_on; auto-restore default off) = at-home wake sync becomes inert.
