**Blocking defect (confirmed twice independently):** `MAX_LIBRARY_SEARCH_RESULTS=500` is enforced only in the worker branch (fuzzy/nearby) of `librarySearchService.ts` (~line 602). The default `contains` mode and whole-words/regex (`matches = Array.from(matcher!(doc, query))`) are **uncapped** and feed a non-virtualized results list — a common word over a big library materializes millions of Ranges/CFIs/excerpts.

**Other perf-relevant defects:** worker terminated on abort → 16 MB warm cache lost on every query edit (`librarySearchWorker.ts` onAbort); `PreparedSearchSection.makeRange` closures pin whole DOM Documents so the "16 MB" prepared-cache accounting is fiction; contains mode re-walks the DOM per query instead of using `getPreparedSection`; section text structured-cloned to worker every request; fuzzy re-segments graphemes every request (only nearby caches `words`); foliate `segmenterSearch` still used for whole-words (the slow collator path).
