Investigated + fixed 2026-09-03, MERGED as PR #6049 (squash `9c235ed8f`, 2026-09-03) (follow-up to [[nearby-bookdrop-v2-pairing-airdrop-sounds]], whose listed open item was exactly "iOS on-device verification incl. the now-live ListenerFailed teardown").

**ROOT CAUSE (device-confirmed, not inferred).** iOS reclaims a suspended app's listening socket but never wakes the accept loop, so `TcpListener::accept` stays pending forever, `ServerEventV2::ListenerFailed` is NEVER emitted, the core never tears the service down, and `status.running` stays `true` on a service no peer can reach. `LocalSendManager`'s visibilitychange handler branched on that flag, so returning to the foreground only called `setLocalSendDiscoverable(true)` on a dead listener. Only the settings toggle (a real `stop()` + `start()`) rebound the socket. Evidence: iPhone awake + Readest `ForegroundRunning` (pid 79404) + settings still showing "Visible as ... Port 53318", yet `nc -z` found NOTHING listening on 53317-53327 on either of its addresses, and 0 `localsend` lines in 2539 syslog lines. **The `ListenerFailed` handler added in PR #6023 pass-5 is dead code on iOS** - keep it (correct elsewhere) but never rely on it.

**FIX = probe, don't trust the flag.** New Rust `service::listener_is_alive(port)` does a 500ms loopback `TcpStream::connect` (the ONLY thing that tells a live listener from a reclaimed one - the OS refuses the connect once the socket is gone; a task-liveness check is useless because the loop is *stuck*, not ended). Exposed as command `localsend_is_alive` -> TS `isLocalSendAlive()`. On becoming visible the manager now probes and, on failure, `stopLocalSend()` then `syncServiceState()` (stop FIRST - `localsend_start` returns the existing service if `guard` is Some). Universal, not iOS-gated: loopback succeeds everywhere else so there is no churn. Tests: Rust `listener_is_alive_follows_the_bound_socket` (bind -> alive, drop -> dead) + `LocalSendManagerPresence.test.tsx` (3 cases, VERIFIED to fail against the old handler).

**Command registration is a 5-PLACE change** (memory previously said 3): `build.rs` ACL list, `lib.rs` invoke_handler, `capabilities/default.json`, `capabilities/webdriver-remote.json`, `permissions/autogenerated/<cmd>.toml`.

**iOS has NO `com.apple.developer.networking.multicast` entitlement** (`gen/apple/Readest_iOS/Readest_iOS.entitlements`). So iOS can neither send nor receive multicast: the ONLY way a peer ever finds the iPhone is that peer's own unicast `/24` subnet scan hitting the iPhone's HTTPS register endpoint. `set_answer_announcements(false)` gates ONLY the multicast answer path, NOT the HTTP register endpoint - so a "stuck answering=false" theory can never explain an unfindable iOS device; a dead listener can.

**Peer `#tag` flickered between #99 and #245** on a multi-homed peer. Not a network glitch: `device_payloads` took `ipv4_host` from the first IPv4 in `get_ranked_channels()`, and the crate ranks by MOST RECENTLY CONFIRMED (`store.rs` `last_confirmed`), so the label followed whichever address answered last. Real cause of two addresses: the iPhone was reachable on Wi-Fi (`192.168.2.99`, en0) AND over the **iPhone-USB link** (`169.254.109.245`, Mac side `en8` 169.254.146.48) - `arp -an` proves it. Fix = choose deterministically: `min_by_key(|ip| (ip.is_link_local(), *ip))` - routable before autoconf link-local, then lowest. Test `device_payload_keeps_the_ipv4_tag_stable_for_a_multi_homed_peer`. NOTE `scan_subnet` is a hard `/24` off the interface's first 3 octets, so a 169.254 link-local peer is NOT reachable by a scan from a different 169.254.x/24.

**Verification recipe for iOS BookDrop (this machine).** `idevice_id -l` for the UDID; `nohup idevicesyslog -u <udid> --no-colors -m LocalSend -m Readest -o <file> &` to stream (NB: `tauri_plugin_log` writes Stdout+LogDir, NEITHER of which reaches the syslog relay, so absence of an app log line proves nothing - use the port probe as the real signal). `nc -z -G 1 -w 1 <ip> <port>` over 53317-53327 is the decisive liveness test. `xcrun devicectl list devices` names the paired phones; `devicectl` is not on PATH, use `xcrun`.

**Build gotcha:** `cargo test -p Readest` panicked with `failed to read plugin permissions` pointing at a DELETED worktree path (`/Users/chrox/dev/readest-fix-windows-onedrive-keychain/...`). The shared `target/` caches each plugin build script's ABSOLUTE permission paths. Fix: `cargo clean -p tauri-plugin-fs -p tauri-plugin-native-bridge -p tauri-plugin-native-tts -p tauri-plugin-webview-upgrade -p tauri-plugin-turso`. See [[worktree-new-rebases-pr-force-push]].

**Presence responsiveness: the GOODBYE (added same day, chrox's design call).** A locked iPhone took 10-15s to leave a peer's list. MEASURED with a 1Hz `nc -z` poll: the phone keeps ANSWERING the unicast re-probe through iOS's whole background grace window (~5-10s), and only then does the 4.5s `PRESENCE_TTL` start. `setLocalSendDiscoverable(false)` buys nothing here - the crate's `answering` flag gates ONLY the multicast answer path (`discovery/mod.rs:482`), never `/register` or `/info`, which is what the re-probe hits. chrox VETOED stopping the service ("keep it just like for now, we just need to remove the screen off devices on the sender's peer devices list").

Fix = an explicit goodbye, NO crate fork needed: `LsHttpClient::new` + `Client::register` are both public, so `service::notify_peers(identity, discovery, port)` POSTs a register to every known peer - real port = "back", `DEPARTURE_PORT` (0) = "going dark". The sender's event pump treats `Register` with port 0 as a goodbye: it stamps the fingerprint into `DepartedPeers` and `device_payloads` filters it. `DEPARTURE_HOLD` (15s) is load-bearing: it must OUTLAST the grace window or the peer's own next answered probe puts it straight back, and it is bounded so a lost hello cannot hide a live device forever (past it, PRESENCE_TTL takes over). Wired into the existing `localsend_set_discoverable` command - NO new command, NO frontend change. Tests `a_goodbye_hides_a_peer_that_is_still_answering` + `device_payloads_drop_a_peer_that_said_goodbye_until_it_says_hello`.

GOTCHA the goodbye introduced: a register REPLACES the peer's stored device (`store.rs` upsert does `known.device = device`), so ANY field the hello DTO omits is a field the peer loses until its next probe. A hand-rolled `RegisterDto` with `device_type: None` made the iPhone draw as a computer for ~1.5s after every unlock (`device_type_str(None)` -> null -> `deviceIcon` falls through to `MdDevices`, whose multi-device glyph reads as a monitor). Fix = `Identity::client_register_dto(port)` so hello/goodbye derive from the SAME identity as `register_dto`, pinned field-by-field by `client_register_dto_carries_the_same_identity_as_the_announce`. RULE: never hand-roll a register payload.

REJECTED carriers: `Client::cancel` with a sentinel session id looks harmless but the crate's cancel handler (`server/v2.rs:467`) cancels a PENDING session from the sender's IP even with no matching id - a goodbye could abort a real in-flight transfer. A new `/bye` route works but costs a fork rev + Cargo.lock + Nix cargoHash. `DiscoveryHandle` has NO remove method, so the sender must filter in `device_payloads`; it cannot delete from the crate's store.

**Local tag was ALSO wrong (same session).** `local_ips()` excluded tun/utun/ppp/wg but NOT `pdp_ip0`, so an iPhone on Wi-Fi with cellular up advertised THREE tags ("#100 #99 #245") and the user could not match any of them against the one a peer shows. Fixed by `is_lan_interface()` (adds `pdp_ip`) plus TS `preferredIpTag(hosts)` in `deviceModel.ts`, which applies the SAME rule as the Rust peer side (routable before link-local, then lowest) so both displays agree on one tag. NB `local_ips()` feeds ONLY the settings tag; the subnet-scan loop in `localsend_announce` uses `if_addrs` directly and is deliberately NOT filtered (excluding a VPN interface could remove a working discovery path).

**Still open:** after the iOS service rebinds, macOS does not re-find it on its own - the 1.5s heartbeat only unicast-reprobes ALREADY-KNOWN channels, and `DevicePickerDialog.refresh` only sweeps the `/24` when `isIOSApp || devices.length === 0`. So the manual Refresh button silently does NOT scan whenever any other peer is listed. Deliberately left alone (out of the confirmed root cause); worth fixing so the button always scans.
